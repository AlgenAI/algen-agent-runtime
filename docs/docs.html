Where Runtime fits#

Runtime is the open-source execution layer of the Algen lifecycle. Projects you design in Agent Studio run on Runtime, and the same agent.yaml runs on your laptop, in CI, or behind your own API.

BuildAgent Studio→ RunAgent Runtime→ DistributeAgent Hub· GovernTraccia

One execution contract, end to end#

Runtime puts governance in the path of execution instead of around it. Every request, model call, tool operation, approval, checkpoint, and output moves through typed contracts with tenant and user context preserved.

Provider-neutral routing

Normalize capabilities, requests, responses, usage, and failures across local and hosted model providers.

Governance in execution

Enforce policies, budgets, permissions, approvals, idempotency, and verification at runtime boundaries.

Durable by contract

Checkpoint runs and workflows, resume approvals, and reconcile side effects without coupling to one store.

Evidence built in

Structured events, immutable audit records, metrics, and redacted traces through OpenTelemetry.

Configuration precedence#

Settings merge in a deliberate order. Later sources override earlier ones; request overrides must be explicitly allowlisted by operators.

Built-in defaults→ YAML files→ ALGEN_AGENT_RUNTIME__ env→ Deployment overrides

Never put a secret in YAML. Use an env:// reference such as env://OPENAI_API_KEY; Runtime resolves it from the environment at the boundary that needs it.

Supported hosted and local providers, capability narrowing, and fallback chains are covered in Providers and Provider compatibility.

Gemini, xAI, Groq and ordered fallback#

From 0.1.0a18 gemini (Google Gemini API), xai (Grok) and groq are provider types, built on the OpenAI-compatible adapter with the vendor base URL and a default secret (env://GEMINI_API_KEY, env://XAI_API_KEY, env://GROQ_API_KEY). base_url and capabilities can be set per entry. Gemini supports embeddings (gemini-embedding-001 by default) and image input; Groq reports strict json_schema support only for gpt-oss models.

agent.yaml · ordered fallback
providers:
  gemini: {type: gemini, default_model: gemini-flash-latest}   # env://GEMINI_API_KEY
  groq: {type: groq, default_model: openai/gpt-oss-120b}       # env://GROQ_API_KEY
agents:
  - name: support-assistant
    default_model: {name: primary, provider: gemini, model: gemini-flash-latest, routing_preference: ordered}
    fallback_models:
      - {name: fast, provider: groq, model: openai/gpt-oss-120b, routing_preference: ordered}

By default (routing_preference: balanced) candidates are ranked by quality tier, observed latency and cost. ordered tries the default model, then each fallback, in declaration order; providers with an open circuit breaker, missing capabilities or exceeded latency or cost limits are still skipped. It describes the agent's whole model list, so configuration that sets it on only some profiles is rejected.

Behaviour change in 0.1.0a18. The router no longer falls back when a provider rejects the request as invalid (HTTP 400 or 422, invalid_request): it raises that error, which does not count against the provider's circuit breaker. Authentication errors, rate limits, timeouts (HTTP 408 is now a retryable timeout), 5xx and other 4xx such as 404 still fall back. ProviderError.status_code carries the provider's HTTP status.

From 0.1.0a21 a model's malformed tool call (arguments that are not valid JSON, not an object, or cut off by the output-token limit) is a retryable InvalidToolCallError from the Anthropic and OpenAI-compatible adapters, not a failed run. The run retries the model call within its retry_policy; a call cut off by the limit is retried with a higher one. The error names the tool and the parse error, never the arguments. Each is recorded as a model.tool_call_invalid audit event and does not count against the provider's circuit breaker.

Runtime a7 · context engineering

Context & memory#

Simple agents use bounded context assembly. Multi-step agents can add recoverable summaries, artifact read-back, structured progress, selected skill guidance, and learned memory. Each capability is explicit and governed; a summary or remembered procedure never grants authorization.

New in 0.1.0a7. This section documents the published 0.1.0a7 package. Install it with python -m pip install "algen-agent-runtime==0.1.0a7"; Studio now requires Runtime 0.1.0a8 or later.

Simple agents#

The built-in default builder allows 16,000 estimated message tokens. It loads session history once and protects system instructions, the latest user request, and the newest complete message group. Tool calls and results stay together. A required input that cannot fit fails with BudgetExceededError; orphan tool results fail with ConflictError. Disabled session memory or a zero item limit prevents loading prior turns.

From 0.2.0b2 a session belongs to the user who first used it. A run that names another user's session_id in the same tenant is refused with NotFoundError (404 over HTTP), as for a session that does not exist, so neither its history nor a session-scoped tool-result cache is reachable. A generated session id is claimed at its first memory write and stays with its user for the memory's retention. The in-memory, Redis and PostgreSQL stores record the owner (SessionOwnership.claim_session; migration 019_session_owners.sql, swept with the memory); a custom memory store without claim_session is not checked and must isolate users itself. Give each user their own session id.

Set a model profile's context_window_tokens and a positive output cap to reserve output, tool definitions, response schemas, profile extensions, and safety headroom before dispatch. Each fallback packs from the original request. Estimates cover normalized text, not a provider tokenizer or image/file costs. Profiles without a configured window retain their previous routing behavior.

Packing, compaction & recovery#

core.context_read requires context.read and returns at most 4,096 Unicode characters per page using artifact_id, offset, and limit. Follow next_offset until null. Reads and replays check tenant, originating run/user, checksum, purpose, availability, and expiry. New opaque ctx_ IDs avoid incidental numeric PII redaction; existing UUID references still work.

Compaction selects at most one bounded prefix per context build. The effective trigger uses the smallest configured builder/allowed-model allowance after reservations; retrieval reserves evidence space, and working state/skill projections count toward the trigger. The recent-group floor and indivisible tool exchanges can prevent compaction. Summary calls use normal policies, allowlists, deadlines, and the same run token/cost budget. Empty, truncated, oversized, tool-calling, or non-reducing summaries fail without advancing the cursor.

By default, canonical history remains inline. archive_compacted_history: true keeps an absolute context_history_offset, protected context_history_pinned messages, the summary, and the remaining tail. Sources move into a linked archive chain before the smaller checkpoint commits. This reduces historical payload duplication; protected inputs, the uncompacted tail, and artifact references may still grow.

Retention determines recoverability. Archived sources can expire, be deleted, or be quarantined while their run and summary survive. Choose durable artifact storage and sufficient retention for pauses and audits. Memory storage is ephemeral. Runtime never bypasses lifecycle or authorization checks to rebuild deleted sources.

Shortened older tool results#

Packing keeps the newest messages that fit max_estimated_tokens and drops older tool exchanges whole, so on a long run the model forgets what it already looked up and may call the same tools again. From 0.1.0a14 an agent can keep those exchanges in shortened form instead. It is off by default.

agent.yaml · context_policy
context_policy:
  shorten_older_tool_results: true
  shortened_tool_result_chars: 1200   # 64 to 16384

When an older exchange no longer fits, each text result longer than shortened_tool_result_chars is cut to that length and ends with a note that it was shortened and already retrieved. The call stays with its results, so the exchange is valid for every provider, and packing goes on with older exchanges while the shortened versions fit. Recent results, required messages and non-text blocks are never changed, and nothing is rewritten in the run history: only the request sent to the model changes. The default and retrieval builders honour it, alongside offload_tool_results and compact_history.

The final packing does not shorten. When a model profile sets context_window_tokens, the request is packed once more against that window just before the call, and that packing drops older exchanges whole. Set the builder budget at or below the model's message allowance so it has nothing left to drop. Builders that override pack(self, messages) keep working: build() passes the policy only when shortening is on.

Working state & progressive skills#

core.working_state_update requires context.write and replaces the five-field record using expected_revision. It follows write approvals and memory-write policies;It changes only the run's own checkpoint, so it declares no side effect and never pauses for approval; memory-write policies still apply, and stale revisions return a small conflict receipt. The bounded assistant projection survives summaries but remains untrusted notes. New runs start empty.

core.skills_load requires skills.read. Its names array replaces the selected guidance (up to four distinct names); an empty array clears it. Configured AgentDefinition.skills contain a name, version, description, instructions, and optional required permissions. Descriptions are visible first; selected bodies are loaded only after authorization and policy checks. Recovery rechecks identity, version, source hash, and permissions.

These are Runtime instruction records, separate from the IDE SKILL.md packs described in Skills & prompts. No filesystem discovery, executable installation, or permission grant occurs. Built-in compaction, working state, and skills require the default or retrieval builder; custom builders keep their own behavior.

Learned memory across runs#

core.memory_recall, core.memory_write, and core.memory_delete require memory.read, memory.write, and memory.delete respectively. Records are scoped to tenant, user, and logical agent name; versions share that namespace. Writes and deletes follow approvals and expected-revision checks. Atomic operation receipts prevent interrupted retries from resurrecting corrected or deleted content.

Recall is explicit, bounded, and based on an exact key or literal case-insensitive substring search. There is no automatic extraction, semantic ranking, injection into every prompt, or conversion of remembered procedures into executable skills. Default writes request one day, capped by the agent's retention policy and anchored to source-run start. Recall/replay checks current revisions and expiry.

Recall is explicit and bounded. By default (learned_memory_policy.recall: substring) it matches an exact key or a literal case-insensitive substring, newest first. From 0.2 recall: semantic ranks records by the similarity of their content embedding to the query, and hybrid adds a weight (hybrid_keyword_weight) for a literal match; both need an embedding_provider and take a min_score. a7 upgrade checklist#

  • Upgrade strict manifest, checkpoint, and event readers together, including workers. New defaulted fields and event types are incompatible with older strict readers.
  • Run the learned-memory migration when using PostgreSQL. Context checkpoint fields themselves require no SQL migration; old checkpoints can recover only their surviving messages.

  • Review reduced payload limits and earlier eviction from serialized-message estimates. Required oversized input now fails explicitly.

Tool behaviour & HTTP tools#

Agents that work through many tool calls, such as coding helpers, need to recover from a failed call, accept a declined action, and call APIs without custom code. Each behaviour is opt-in on the agent definition; defaults keep the earlier fail-the-run behaviour.

Declarative HTTP API tools#

http_tools turns an HTTP API operation into a tool. Path placeholders must be required parameters and the host cannot be templated. Credentials are env:// references resolved per call. Requests use the SSRF-safe client without redirects, and settings validation refuses a tool whose host is not in security.allowed_http_hosts. GET is a read; other methods are external side effects that need approval under the default policy. A non-2xx response returns ok: false to the model instead of failing.

Calling an API as the signed-in user#

From 0.1.0a18 auth.type: caller sends the credential the host passed for this run (credentials of the caller) instead of one deployment secret, so the API applies that user's permissions.

agent.yaml · auth.type: caller
http_tools:
  - name: lms.my_courses
    description: List the courses the signed-in user is enrolled in.
    url: https://lms.example.com/api/me/courses
    auth:
      type: caller
      credential: lms_token       # key in the run's credentials (default: authorization)
      # header_name: Authorization  (default)
      # scheme: Bearer              (optional prefix)
  • One key per API. Forward a token only to an API that is its audience. Any caller tool can name any key in the run's credentials, so which API receives which token is decided by this configuration alone.
  • Fails closed. A missing or blank credential, or one that is only the scheme, fails with authentication required before any request, and the ledger records the call failed, not indeterminate. That is the case for runs started through the HTTP API, workflow tool steps, and runs resumed or recovered without credentials. A value with another scheme or a control character is refused without being echoed.
  • Declared origin only. The credential goes only to the URL's scheme, host and port; link-header pagination to another origin fails the call. Cookie, Host, Proxy-Authorization, hop-by-hop and framing headers are refused as header_name, headers may not set the auth header, and token, username and password are refused with caller.
  • Never cached. A call whose context carries caller credentials is never served from, or stored in, the tool-result cache.

Also in 0.1.0a18: a path value that is empty, . or .. (also percent-encoded) is refused, so a model argument cannot move the call, and a forwarded credential, to another path on the same host; and a query string in the url template is merged with the query templates and pagination parameters instead of being dropped. See HTTP API tools.

Delegating to another agent#

core.subagent hands a bounded task to another agent of the tenant, as a child run for the same tenant and user with the parent's credentials; its result (run_id, status, session_id, output, ...) is the call's result. From 0.2.0b2 it takes two opt-ins: the deployment registers it with runtime.subagent.enabled: true (default false), and each agent that may delegate lists core.subagent in enabled_tools, agents.delegate in tool_permissions and the agents it may call in delegates. With the setting off, an agent that lists the tool fails the container's component check; describe and check list the tool when it is on.

agent.yaml · delegation
runtime:
  subagent:
    enabled: true                    # register core.subagent; off by default
    max_depth: 3                     # delegations allowed in one chain (1 to 10)
agents:
  - name: planner
    enabled_tools: [core.subagent]
    tool_permissions: [agents.delegate, crm.read]
    delegates: [researcher]          # the agents it may delegate to; "*" allows any
  • Allowlist. An agent delegates only to the agents in its delegates (AgentDefinition.delegates): empty, the default, allows none, and "*" allows any agent of the registry. Another agent is refused with PolicyDeniedError.
  • No wider permissions. The delegate's tool_permissions must be within the caller's, so a planner with crm.read cannot reach crm.write through a delegate that has it.
  • Depth from lineage. The child's RunRequest.parent_run_id is the calling run, and the Runtime counts the nesting from it; only runs core.subagent started count. A call at max_depth is refused with PolicyDeniedError. The model's depth argument is accepted for older prompts and ignored.
  • Never reused. The tool is volatile and non-idempotent: each call starts a new child run, never served from the tool-result cache, retried or held back by the repeat guard.

A host that builds an AgentRuntime itself registers the tool with runtime.tools.register(subagent_tool(runtime, max_depth=3)) (algen_agent_runtime.tools.subagent). On a build_container container, do not also set runtime.subagent.enabled: true: registering it twice raises ConflictError. See Delegating to another agent.

Workflow tool steps#

A workflow handler node can call any registered tool, including an HTTP API tool, with handler: tool:<name> and an arguments map. The call goes through the same permissions, approval, and idempotency checks as an agent's tool call, and its result is stored under the node's output_key.

From 0.1.0a22 an approval-required tool step is approved only by the approval node's recorded status, so no other step or input can approve it. An approval covers the step, not its arguments: read them from what the approver saw, and from {{approval.parameters.*}} when the approval can be modified. check warns when a step reads anything else, and each covered call emits workflow.tool.authorized with digests of its arguments and of the approved parameters. Node output keys must be unique.

From 0.1.0a23 the step needs every approval that gates it, the nearest approval on each path to the step, to have approved; an earlier approval behind a rejected one never stands in for it, even with rejection_policy: continue. Approvals that are ready at the same time are asked one at a time.

From 0.2 an approval covers the exact call, not just the step. The pause shows the approver each gated step's call (calls: tool, version, fingerprint, resolved arguments and arguments_sha256), and the decision is bound to that call, or to the call resolved with the approver's modified parameters. The step then runs only with exactly those arguments; otherwise it is refused with ApprovalMismatchError and workflow.tool.refused (approval.arguments_mismatch, approval.arguments_unbound or approval.modification_ignored). Template the arguments from what the approval shows ({{approval.parameters.*}}, review_from values, literals) and put the approval after the nodes that produce them: check reports APPROVAL_ARGUMENTS_UNBOUND as an error. binding: step on the approval keeps the old behaviour and is discouraged. Each covered call emits workflow.tool.authorized with its binding and digests of its arguments and of the approved parameters. Node output keys must be unique. See Approvals bind the exact call.

Runtime a14 · tool-call guards

Tool-call guards#

Guards keep a model from wasting a run on calls that cannot succeed, on reads it already made, or on tools when it should be answering. A refused or held-back call never runs; it still answers the model's tool call, with a note saying what to do instead. Their state (tool_refusals, tool_call_counts, seen_read_calls) is kept in RunState, so it survives an approval pause and a restart, and a checkpoint without it still loads. Except for the schema check, every guard is off by default.

New in 0.1.0a14. Install it with python -m pip install "algen-agent-runtime==0.1.0a14". Studio's Runtime floor is still 0.1.0a13, so these settings take effect only where 0.1.0a14 or later is installed.

Repeats, limits and room to answer#

With repeat_guard, a successful write, external or destructive call lets every read run again, and a failed read is forgotten, so its retry runs. This is separate from the run-scoped tool cache: the cache hides a repeat from the model, the guard tells the model it is repeating. An answer takes two steps and each further tool call two more; with wrap_up_policy on, the Runtime computes the calls still affordable after each tool call and adds the notice at or below tool_calls_left, whatever the result's type. There is no notice while continuation_policy still has automatic extensions left.

Credentials of the caller#

From 0.1.0a15 a tool that acts as the signed-in user, for example by calling the host's own API, reads the user's credentials from context.credentials. The host passes them per run, as the keyword-only credentials= of Runtime.start, run and resume; the Runtime protocol has the same keyword, so a host's own implementation should accept it. From 0.2.0b2 AlgenAgentRuntimeClient.run, run_sync and stream take the same credentials= and pass it to the run.

host · pass the caller's credentials
result = await runtime.run(request, credentials={"authorization": request_headers["authorization"]})
# After an approval or clarification pause, supply them again: none are kept.
await runtime.resume(run_id, tenant_id, {"decision": "approved"}, credentials=fresh_credentials)
crm_agent/plugin.py · a tool that acts as the caller
@crm.tool(read())
async def my_open_tickets(context: ToolContext) -> list[Ticket]:
    """List the open tickets assigned to the signed-in user."""
    authorization = context.credentials.get("authorization")
    if authorization is None:
        raise ToolExecutionError("authentication required: sign in again and retry")
    client = await crm.client()
    return await client.tickets(assignee="me", headers={"Authorization": authorization})
  • context.credentials is a read-only Mapping[str, str], empty by default: a private copy of what the host passed, so changing the host's dict afterwards changes nothing.
  • Memory only, for the run's current execution. They are never written to run state or checkpoints, events, audits, spans, logs, caches or the model's context, and are left out of ToolContext's repr, model_dump, equality and hashing. Do not put them in a tool's result or error message.
  • They are dropped when the run pauses for approval or clarification and when it ends. A resumed run sees only the credentials passed to resume; resumed without any, or recovered by Runtime.recover() after a restart, it sees an empty mapping. Answer that with an “authentication required” error rather than acting without the user's authority.
  • All tool calls of a run, parallel ones included, see the same credentials; concurrent runs never see each other's. core.subagent passes the parent's credentials to its child run; a host's own delegation tool should call runtime.run(child_request, credentials=context.credentials).
  • ToolContext.secrets is different: static deployment configuration, the same for every run. In tests, fake_tool_context(credentials=...) sets the mapping.

Known limitations. Workflow tool steps, and the agent runs a workflow starts, get no credentials, and the HTTP API's run and resume endpoints forward none: a host that needs them calls the Runtime through the Python API. A run recovered after a restart has none. A child run inherits them only through core.subagent. See Credentials of the caller.

def create_hooks(**_: Any) -> WorkflowHookRegistry:
    hooks = WorkflowHookRegistry()

    def propose(context: Any) -> dict[str, Any]:
        change = str(context.state.values["question"])
        return {"change": change, "parameters": {"change": change}}

    def apply(context: Any) -> dict[str, Any]:
        approval = context.state.values["approval"]
        return {"status": "applied", "parameters": approval["parameters"]}

    hooks.register_builder("approval.propose", propose)
    hooks.register_handler("approval.apply", apply)
    return hooks

Service workflow lifecycle#

From 0.1.0a16 the service looks after the workflow runs it starts. A run started through the HTTP workflow API (POST /v1/workflows/{name}/runs) records owner: "workflow_service" in its checkpoint (the new optional WorkflowExecutionState.owner). Runs an application starts with its own executor have no owner, and the service never touches them.

  • Recovery on start. With runtime.recover_incomplete_runs and runtime.recover_service_workflows (both default true), startup recovers each owned top-level run that was pending or running through executor.recover, with the exact configured manifest (same name, version and content fingerprint), hooks loaded only from security.trusted_plugin_prefixes, and each node's recovery_policy (an interrupted node retries only with retry; otherwise the run fails closed). A run whose manifest changed or is no longer configured, or whose hooks are not trusted, is left untouched and logged. Child workflows are recovered through their parent; waiting runs are not resumed. If recovery fails, the service still starts and readiness reports workflow.recovery as degraded. Recovery is single-node: it takes no lease on a run, so enable recover_incomplete_runs on exactly one process per database (or schema) and set it to false on every other replica, until the leases planned for 0.3. From 0.2.0b2 a second process that recovers the same database by mistake no longer fails its start or the interrupted run, but it can repeat work.
  • Expiry of waits. The maintenance sweep (maintenance.expire_paused_workflows, default true) expires an owned run's approval wait past its expires_at (workflow.approval.expired) and, with maintenance.clarification_timeout_seconds set, an input wait older than that (workflow.input.expired, the node fails with workflow input expired). It goes through the engine's own expiry path, so rejection policies, dependents, checkpoints and the webhook behave as for a late decision, and repeated or concurrent sweeps expire a wait once. It runs only in the serving process (maintenance.enabled) and reports expired_workflow_pauses; the maintenance command does not drive workflows.
  • Drain. On shutdown the workflow service is drained before the runtime: running workflows get shutdown_grace_seconds to finish or pause, and unfinished runs keep their last checkpoint, recoverable, instead of being marked cancelled. The agent run a workflow step waits on is drained by the runtime, not cancelled. Starting or answering a workflow run during shutdown returns 409.

An application that drives its own executor does the same itself: executor.recover(...) on start, and executor.expire_pause(manifest, workflow_id, tenant_id=..., input_timeout_seconds=...) on its own schedule. It ends an expired approval or input wait, including one inside a child workflow, which the parent then consumes, and returns a run that is not waiting, or not yet expired, unchanged. MultiAgentWorkflowExecutor also gains pause_expired, manifest_matches, the interrupted constructor argument and run(..., owner=...); WorkflowService has recover, expire_paused, drain and idle, and Container.attach_workflows attaches one.

Upgrade note: runs without an owner. Workflow runs started through the HTTP API before 0.1.0a16 have no owner, so they are neither recovered on start nor expired by the sweep. Decide or answer them through the API, or recover them once with executor.recover. See Multi-agent workflows and Operations · workflow recovery.

Workflows are fingerprinted. A paused workflow resumes only against the same manifest name and version that started it, so a redeploy cannot silently change an in-flight run. See Multi-agent workflows for recovery semantics.

Changed in 0.1.0a19. An agent node's unparseable JSON output goes through the repair loop up to max_repairs (more model calls) and, once repairs run out, fails with VerificationError instead of ConfigurationError. Workflow tool: steps work under algen-agent-runtime serve. Agent nodes can pass the run's files with pass_attachments; see File attachments.

The Runtime's workflow guide (0.1.0a21) documents the hook factory's keyword arguments under serve (container, manifest, environment), every WorkflowHookContext field and which hooks receive it, each hook kind's signature, and how serve loads hooks and recovers workflows: hook provider reference. Its MCP guide documents the tool-result shape, and its operations guide has a route-by-route scope table.

Runtime a16 · conversation turns

Conversation turns#

A conversation turn is one user message and the assistant message that answers it. From 0.1.0a16 the built-in runtime conversation handler, which runs one agent run per turn, streams the answer as it is written, pauses the turn when its run needs an approval or an answer, and resumes into the same assistant message, also after a restart.

New in 0.1.0a16. Install it with python -m pip install "algen-agent-runtime==0.1.0a16". Studio's Runtime floor is still 0.1.0a13, so this behaviour applies only where 0.1.0a16 or later is installed.

Streaming#

When conversation_streaming.enabled is true (the default) and every model the agent may use can stream, the turn's run is started with stream=True and its text reaches GET /v1/conversations/{id}/events as assistant.message.delta events, with data {message_id, delta}. A turn whose models cannot stream gives only the final message, as before.

agent.yaml · conversation streaming (defaults)
conversation_streaming:
  enabled: true           # false: only the final message, and turns use the model-response cache again
  delta_interval_ms: 50   # at most one delta event per interval per turn; smaller deltas are coalesced
  delta_max_chars: 2048   # largest delta event; a fuller buffer is sent at once, in pieces of this size

Deltas are provisional and may include text the model wrote before a tool call: the assistant.message.completed message is the record. They carry only model text, never tool arguments or results, and are not audited. Streamed model calls bypass the model-response cache, as streaming runs always have.

Approvals and questions in a turn#

When the turn's run awaits an approval or a clarification, the assistant message moves to awaiting_approval or awaiting_input. Its pending action, also in the assistant.message.awaiting_approval or assistant.message.awaiting_input event, carries what a UI needs to ask: turn_id, run_id, approval_id, tool, proposed_action, side_effect_summary, risk, expires_at, options, redacted_parameters (as in the run's approval.required event; never raw arguments) and the tool's parameters_schema, or the question to answer.

One waiting turn per conversation#

Only one turn per conversation can wait. A new message while one waits is refused with 409 naming the waiting turn id: answer it, or cancel it with DELETE /v1/conversations/{id}/active-response, which also cancels the paused run. Deleting the conversation cancels it too.

Restarts#

The pending action is stored on the assistant message and the paused run in the run store, so a restart loses neither and nothing re-runs. recover() leaves a waiting turn waiting, and the user can answer it after the restart. If the run was resumed but the process stopped before the message was updated, recovery follows the run to its end instead of running it again; if the run ended while the turn waited, the turn ends with that outcome. ConversationService.reconcile_pending_turns() does this, and the maintenance sweep runs it for turns whose paused run it expires (reconciled_pending_turns). A custom handler opts in by implementing ResumableConversationHandler (resume, follow, settle, pending_state, cancel_pending).

Credentials of the caller#

ConversationService.submit(..., credentials=...) and respond(..., credentials=...) pass the caller's credentials to the turn's run for its tools, exactly as Runtime.start and resume do (see Credentials of the caller). They are held in memory only, never stored, emitted, audited or logged; a turn that pauses drops them, so pass them again when answering. The HTTP routes never forward request headers as credentials. A custom handler receives them by accepting a credentials keyword argument in handle; passing credentials to a handler that does not is a ConfigurationError.

Runtime a19 · file attachments

File attachments#

From 0.1.0a19 an agent can read files a caller gives it: a photo of an ID document, a scanned invoice, a screenshot or a PDF. The model sees the file natively (vision or PDF input) in the same call as the question. Files are passed by reference to an uploaded artifact, never as inline bytes. Attachments are off by default: an agent or workflow opts in, and text-only runs are unchanged.

New in 0.1.0a19. Install it with python -m pip install "algen-agent-runtime==0.1.0a19" or later. Send attachments only once every API process and worker runs 0.1.0a19 or later; earlier replicas can read what it stores, but cannot load the files.

Opt in#

agent.yaml · attachments
agents:
  - name: kyc-reader
    attachments:
      enabled: true
      types: [image/png, image/jpeg, image/webp, image/gif, application/pdf]  # the default
      max_count: 5          # default 5, at most 32
      retention: turn       # turn (default) or session
security:                   # the deployment's outer limits; an agent can only narrow them
  allowed_attachment_types: [image/png, image/jpeg, image/webp, image/gif, application/pdf]
  max_attachments_per_run: 10
  max_attachment_bytes_total: 20971520   # 20 MiB per run
  upload_scanner: basic                  # none (default) or basic

GET /v1/agents and GET /v1/workflows return each one's attachments policy. Show an attach control only when it has enabled: true and its default or fallback model reports the capability (images, or files for PDF), and use types as the file picker's accept list.

Checked before any model call#

  • The agent (or workflow) opted in, and every artifact exists in the caller's tenant and is available.
  • The real type, read from the bytes, is allowed by the agent and by security.allowed_attachment_types. Formats models do not read, such as HEIC, are refused; nothing is converted.
  • Count and total size are within max_count, max_attachments_per_run and max_attachment_bytes_total; images are at most 5 MB and 8000 px a side, PDFs at most 32 MB.
  • A configured model can read them. Models without the capability are skipped, fallbacks included; a file is never silently dropped.

Hosts can veto or filter files with a policy on the attachments point. It receives {artifact_id, media_type, name, size_bytes, sha256} per file, never content.

References in history, bytes at dispatch#

History, memory, checkpoints, conversation records, events, audits and spans hold only file blocks (artifact_id, media_type), never base64, even with telemetry content capture on. The bytes are loaded onto a copy of the request just before each provider call. A file deleted or expired since becomes a note instead of failing the run. With retention: turn the file is replaced by a note in session memory after the turn, so later turns do not pay for it again; context budgets count about 1,600 tokens per image and 8,000 per PDF.

Tools and workflows#

ToolContext.attachments lists the run's files and await context.read_attachment(artifact_id) returns one with its bytes, from the run's tenant only. In algen-agent-tools, documents_toolkit(artifact_loader=runtime_attachment_loader) extracts the text of an attached document through the document security checks. A workflow declares attachments: {enabled: true}, and each agent node that should see the files sets pass_attachments: true; settings validation fails when a node passes files to an agent that does not accept them.

Scanning and retention#

Uploads start pending_scan and cannot be attached until something makes them available. security.upload_scanner: basic runs BasicArtifactScanner on each upload: it quarantines an image or PDF whose bytes are not what it claims, is malformed or exceeds model limits, and records scan evidence before the status changes. It does not inspect content; add your own ArtifactScanner for that. ID documents and similar uploads are sensitive personal data: give them a short expires_in_seconds and schedule ArtifactStore.purge_expired().

# Build an Algen agent project

Start by choosing the smallest topology that fits: one agent for a single governed conversation, or
a Runtime `WorkflowManifest` for coordination. Scaffolding is available via the CLI:
`algen-agent-runtime new <name> [--template agent|approval|workflow]`. Read `references/project-shape.md`;
for a workflow, also read `references/workflows.md`. Use `$algen-agent-connector` when external tools,
safe starter tools (`algen_agent_runtime.tools.starter`), databases, retrieval, MCP, or remote APIs are part
of the request.

Prefer configuration for provider routing, policies, memory, retrieval, storage, telemetry, and
workflow topology. Keep only domain-specific payload builders, validators, schemas, predicates, and
deterministic handlers in the project's hook provider. Never implement a second scheduler or a
Studio-specific workflow dialect. For automated CI and headless evaluation, use non-interactive workflow
options (`--approve-all`, `--reject-all`, `--answers-file PATH`).

Produce an importable project with secret references, bounded execution, deterministic offline
tests, documented optional dependencies, and a small runnable entry point. A project intended for
Studio must keep its Runtime configuration and `WorkflowManifest` authoritative. Studio sees only
what the settings declare, never constructor arguments, so:

- Every name an agent uses (`enabled_tools`, `planning_strategy`, `response_composer`, `verification_policy.verifiers`,
  `context_builder`, `guardrail_policy.policies`, provider types) must come from the Runtime,
  the settings (`http_tools`,

Usage metering#

A deployment that bills or rations model use passes a UsageMeter to build_container(settings, usage_meter=...) (or ModelRouter(usage_meter=...)). It is a deployment setting, with no agent.yaml field. The router reserves before every provider dispatch and settles afterwards, so agent steps, retries, fallbacks, schema repairs, streamed calls and history compaction are all charged; a failed, errored or cancelled call is released, and a cached response is not charged. Without a meter nothing changes.

app.py · usage meter
from algen_agent_runtime import MeterRefusedError

class CreditMeter:  # satisfies UsageMeter
    async def reserve(self, *, max_input_tokens: int, max_output_tokens: int) -> object:
        hold = await wallet.hold(max_input_tokens + max_output_tokens)
        if hold is None:
            raise MeterRefusedError("You have used this month's model allowance.")
        return hold

    async def settle(self, ticket: object, usage: TokenUsage) -> None:
        await wallet.charge(ticket, usage.input_tokens + usage.output_tokens)

    async def release(self, ticket: object) -> None:
        await wallet.cancel(ticket)

container = build_container(settings, usage_meter=CreditMeter())

max_input_tokens is the router's estimate_request_tokens for the chosen model (about four characters a token, tools and schema included) and max_output_tokens the request's output cap; settle receives the provider's reported usage. To refuse, raise MeterRefusedError: the call is not retried, not passed to a fallback model and not counted against provider health. The run ends failed with the reason on RunState.error, a budget.refused event and audit record, run.failed with reason: budget_refused, and budget.refused on the agent.run span. Any other exception from reserve is an internal error, not a refusal. The meter holds its own state, so a run resumed after approval is charged only for the calls it makes after resuming. It replaces the Algen Agent Harness's CreditMeter and MeteredProvider: there is no provider to wrap, and the reason is read from the run's error.

app.py · usage meter
from dataclasses import dataclass

from algen_agent_runtime import MeterCall, MeterRefusedError
from algen_agent_runtime.orchestration.container import build_container
from algen_agent_runtime.types.contracts import TokenUsage

# Credits per token, by model; anything else costs 1.
MODEL_WEIGHTS = {"gpt-4.1": 4.0, "gpt-4.1-mini": 1.0}


@dataclass(frozen=True)
class Hold:
    account: str
    call: MeterCall  # kept for settle, which receives only the ticket
    hold_id: str


class CreditMeter:  # satisfies UsageMeter
    def __init__(self, wallets) -> None:
        self._wallets = wallets

    async def reserve(
        self, *, max_input_tokens: int, max_output_tokens: int, call: MeterCall
    ) -> object:
        # Charge the workspace when the host passed one in RunRequest.metadata, else the tenant.
        account = call.metadata.get("account_id") or call.tenant_id or "unattributed"
        weight = MODEL_WEIGHTS.get(call.model, 1.0)
        hold_id = await self._wallets.hold(account, (max_input_tokens + max_output_tokens) * weight)
        if hold_id is None:
            raise MeterRefusedError("You have used this month's model allowance.")
        return Hold(account=account, call=call, hold_id=hold_id)

    async def settle(self, ticket: object, usage: TokenUsage) -> None:
        assert isinstance(ticket, Hold)
        weight = MODEL_WEIGHTS.get(ticket.call.model, 1.0)
        tokens = (usage.input_tokens + usage.output_tokens) * weight
        await self._wallets.charge(ticket.account, ticket.hold_id, tokens)

    async def release(self, ticket: object) -> None:
        assert isinstance(ticket, Hold)
        await self._wallets.cancel(ticket.account, ticket.hold_id)


container = build_container(settings, usage_meter=CreditMeter(wallets))

max_input_tokens is the router's estimate_request_tokens for the chosen model (about four characters a token, tools and schema included) and max_output_tokens the request's output cap; settle receives the provider's reported usage, with estimated_cost_usd filled in when the provider has configured rates.

XLSX text is one line per row under --- Sheet: <name> ---, a formula contributes its last calculated value, date and time cells come out as ISO dates and times, and a sheet longer than max_rows_per_sheet (5,000) is cut and reported as document.truncated. PPTX text is one line per paragraph under --- Slide <n> ---, without speaker notes or comments; HTML text is the visible body only. Any other suffix raises ValueError naming every supported format; legacy .doc, .xls and .ppt are not supported.

Known limitations. Not detected yet: in XLSX, the ;;; number format and a font colour that matches the cell fill; in HTML, styles from stylesheets, font-size: 0 !important, opacity: .0, color: transparent and off-screen positioning; in PPTX (and DOCX), images linked from outside the file. See Untrusted document inspection.

Policy bundles & fail modes#

The policy engine runs at eleven boundaries. From 0.1.0a18 each boundary has an explicit fail mode for a policy that raises or times out, a deny always beats an approval requirement, and an operator can distribute rules every agent runs as an Ed25519-signed bundle verified at start-up.

New in 0.1.0a18. Install it with python -m pip install "algen-agent-runtime[encryption]==0.1.0a18"; verifying signatures needs the encryption extra, unsigned bundles do not. Studio's Runtime floor is 0.1.0a17, so this applies only where 0.1.0a18 or later is installed.

Boundaries and fail modes#

When a policy raises, returns something other than a PolicyDecision, or runs past policies.evaluation_timeout_seconds, the boundary's fail mode decides. closed refuses the value as a deny would (reason_code: policy.error, a PolicyDeniedError); open skips only the failed policy and lets the others decide. A policy that raises PolicyDeniedError has decided: that is a denial in either mode.

A deny wins#

At one boundary a deny from any policy now wins over an earlier policy's require_approval or require_clarification: the later policies still run, so a call a bundle denies is refused instead of first being put to an approver. A deny at plan_tool now refuses the call; before, only require_approval was honoured there and a denial waited until before_tool, after an approval could have been asked for.

Redaction and refused tool calls#

  • Bearer tokens and card numbers. The secrets policy also redacts bearer tokens (Bearer <token> with a digit or separator in the token), and the pii policy redacts card numbers as [REDACTED_CARD]: digit runs with a card network's prefix and length that pass the Luhn check. As with any redaction of tool arguments, such a value in a tool call's arguments refuses the call at before_tool. Pass credentials as env:// references or caller credentials, never as argument values.
  • UUIDs no longer refused. The pii policy no longer redacts digit runs inside UUIDs, hashes and other tokens as phone or Aadhaar numbers (an identifier must not touch a letter, digit, _ or -). Before, roughly one in sixty tool calls carrying a run, record or order UUID was refused at before_tool.
  • Wider redaction. redact() (audit metadata, logs, conversation records) also redacts key=value credential assignments; approval requests redact bearer tokens and key=value credentials inside argument values; the text of an error a tool raised is redacted for credentials; and opt-in telemetry content is redacted for emails, phone, Aadhaar and card numbers, and no longer carries a reply's credentials before after_model redacts it.
  • Phone and Aadhaar numbers (0.2.0b2). A 12-digit number, whole or in three groups of four, is an Aadhaar number only when it starts 2 to 9 and its last digit is its Verhoeff check digit. Ten digits starting 6 to 9 are a phone number only after +91, 91 or a trunk 0, grouped 5-5 (98765 43210), or with a phone word (phone, mobile, call, tel, WhatsApp, ...) shortly before them or in the field's name. A bare 10-digit tracking, order or chat id passes; a deployment that relied on it being masked names the field, adds phone context or uses its own DLP policy.
  • Secrets and injection (0.2.0b2). The secrets policy redacts a key: value or key=value credential only when it is written as code or configuration (with =, a quoted or identifier key, or a value that reads as a credential), so prose such as “the secret: consistency” is left alone. prompt_injection and tool_result_injection refuse an instruction addressed to the assistant that aims at its own rules (“please disable your guardrails”, “reveal your system prompt”); a question that only mentions bypassing a policy passes, and “ignore previous instructions” is still refused anywhere.
  • Declared identifiers (0.2.0b2). A tool schema field declaring "format": "identifier", or "x-pii": false when it already has a format, keeps a one-token value (a chat, message, order or tracking id) at plan_tool, before_tool, after_tool and when the result is read again from history; values with whitespace are still screened. Both markers are removed from the schemas sent to model providers. guardrail_policy.pii.exempt_entities (for example [phone]) turns kinds off for one agent everywhere. See What the pii guardrail redacts.

Behaviour changes. A policy that raises or times out now ends its boundary with a policy.error deny instead of its own exception propagating. A deny beats an approval requirement at the same boundary, and a deny at plan_tool refuses the call. A bearer token or card number in a tool call's arguments refuses the call. Approvals are persisted before control returns, so a process restart never loses a pending decision. They appear in two places:

  • Tool approvals — a single-agent run reaches a side-effecting tool call, moves to awaiting_approval, and resumes with a decision.

Runtime a17 · side-effect operations

Side-effect operations#

Every side-effecting tool call is reserved in the tool-execution ledger under its idempotency key (<run_id>:<tool_call_id>) before it runs. A call that fails without a clear outcome (a timeout, or a connection dropped after the request left) is recorded indeterminate; a call the process stopped in the middle of stays started. Neither is ever retried by itself. From 0.1.0a17 an operator can find these calls, record what happened, ask the tool, or undo the effect, and an agent can wait for that decision.

New in 0.1.0a17. Install it with python -m pip install "algen-agent-runtime==0.1.0a17". Studio's Runtime floor is still 0.1.0a13, so this applies only where 0.1.0a17 or later is installed. PostgreSQL ledgers get migration 014_tool_execution_reconciliation.sql on startup.

From 0.1.0a19 a tool that refuses before sending anything raises ToolNotAttemptedError (since 0.1.0a18) or PolicyDeniedError, and the call is recorded failed, not indeterminate: nothing needs reconciling, and it can be retried. algen-agent-tools 0.2.0a7 marks a provider's definite rejection (a 4xx other than 408, a refused SMTP recipient) the same way; timeouts and 5xx stay indeterminate.

What happens to the run#

By default (tool_policy.on_indeterminate: on_error) an indeterminate call is handled like any failed call: the run fails, or with on_error: return_to_model the model hears that it failed. Settling the call later is record-keeping only; an ended run is never reopened.

agent.yaml · wait for the operator
agents:
  - name: crm-assistant
    tool_policy:
      on_indeterminate: pause   # default: on_error

With pause the run pauses in the new awaiting_reconciliation status (a paused status, RunStatus.AWAITING_RECONCILIATION) with a tool.reconciliation_required event and a pause_payload of kind: tool_reconciliation naming the tool, call and idempotency key, never the arguments. Settling the call continues the run: completed gives the model the recorded result (screened like any tool result), or a note that the call took effect when no result was recorded; failed gives it a ToolCallNotApplied tool error; a successful compensation gives it ToolCallCompensated.

invoking_tool→ awaiting_reconciliation→ completed · failed · compensated→ run continues

A paused run keeps its remaining deadline and is not expired by the maintenance sweep; cancel it to give up. In a parallel batch the other calls are recorded first and the run pauses on the first unknown one. Read-only tools never pause a run, and a resumed run has no caller credentials, as after recovery. Workflow tool steps do not pause for reconciliation.

Rules#

  • Compare-and-set. Each decision changes the ledger only if the status is still the one read, so of two concurrent decisions exactly one wins and the other gets 409. expected_status makes a request fail with 409 if the call changed since you looked.
  • Stale started calls. A started call may still be running. It can be resolved or reconciled only after ToolReconciliation.stale_started_after (default 10 minutes) without change; before that the answer is 409. Filter the list with min_age_seconds.
  • Late outcomes. The ledger's complete and fail change only a started record, so a call that finishes after an operator settled it cannot overwrite the decision; it is logged as tool_execution_late_outcome_ignored.
  • Record. Each decision appends {action, previous_status, status, actor_id, reason, result_reference, at} to the record's resolutions.
  • Re-execution. A call settled failed counts as not having happened: if a still-running run replays it, it runs again, as any failed call does.
  • Retention also keeps runs with compensating or compensation_failed tool executions.

    # result.value is None for an indeterminate call

async def update_owner(account_id: str, owner: str, context: ToolContext) -> Receipt:

  • reconcile answers completed (with value, which must fit the output schema), failed (it did not and will not happen) or unknown. It must only read, since it may run more than once, and it runs within the tool's timeout. Keep detail short and free of arguments and secrets: it is stored and audited.
  • Replay. When a recovered run replays a call that is still started or indeterminate, the executor asks the hook first (unless reconcile_on_replay=False): completed records the result and the run continues without running the tool again; failed fails the call without running it; unknown, an error or a timeout leaves the record, and the run fails or pauses as configured. The decision is recorded with actor runtime.
  • @tool and build_tool take reconcile= and compensation=; Tool(definition, handler, compensation, reconcile=..., reconcile_on_replay=True) takes the same hooks. Both hooks get the call's ToolContext without caller credentials, and describe shows reconcile: true and compensation: true. Built-in HTTP API, email and MCP tools have no reconcile hook yet.

Compensation#

Compensation runs only when an operator asks for it. The Runtime never compensates by itself, not on run failure, cancellation or recovery: it cannot tell whether a failure makes earlier effects wrong, a failure seen during recovery may be transient, and undoing an indeterminate call can itself cause a side effect when the original never happened. The ledger moves to compensating (compare-and-set) before the handler runs, so one request runs it at most once and a concurrent request gets 409. Success records compensated; an exception records compensation_failed with the error type, and only that status may be compensated again. If the process stops while the handler runs, the call stays compensating and is never compensated again by itself: settle it with resolve. For an indeterminate call the handler gets ToolResult(value=None, metadata={"execution_status": "indeterminate"}), so it must cope with an effect that may never have happened; make it idempotent with the idempotency key.

OAuth for remote MCP servers#

Hosted MCP servers such as Slack, Linear and Jira accept only OAuth access tokens. With auth: {type: oauth} on a streamable_http or sse server, the Runtime runs the authorization code flow with PKCE (S256), keeps the tokens per tenant or per user, refreshes them, and sends the access token on every request. It is off by default: servers without auth, and fixed auth_token_ref tokens, work as before.

Storage, encryption and limits#

  • storage.mcp_oauth_token_store: memory (the default) forgets every connection on restart, and a callback must reach the worker that started the flow: development and single-process deployments only.
  • postgres stores tokens and pending authorizations (migration 012_mcp_oauth.sql) as AES-256-GCM ciphertext bound to their tenant row. It needs the encryption extra (pip install 'algen-agent-runtime[encryption]') and storage.mcp_oauth_encryption_key, an env:// reference to a base64 32-byte key; rotate by listing the old key under mcp_oauth_previous_encryption_keys. Back the key up with the database: without it, users must connect again.
  • Tokens refresh refresh_margin_seconds before expiry and once on a 401; a refresh the provider rejects removes the connection. Metadata, token and revocation requests use the SSRF-guarded client, so add the authorization server's hosts to security.allowed_http_hosts.
  • At startup an OAuth server usually has no connection to list tools with, so it is recorded in degraded_dependencies (startup does not fail, even with required: true) and its tools are listed when the first connection completes.

Limits. Dynamic client registration (RFC 7591) is not supported: register a client with the provider and configure its client_id. Run more than one API worker only with the PostgreSQL store. Tokens, refresh tokens, PKCE verifiers and client secrets never reach tool code, the model, logs, events, spans or audit records. See OAuth for remote MCP servers.

Steering a running run#

From 0.1.0a18 a user can add to a run while it works. runtime.steer(run_id, tenant_id, text), or POST /v1/runs/{run_id}/steer with {"text": "..."} (runs:write; for a conversation turn's run, only the conversation's owneronly the run's user, the conversation's owner for a turn), queues a message and answers 202 with {"run_id", "steer_id", "status": "queued"}.

  • Delivery. Before the next model call, after the results of the model's last reply, as one user message, checked at the input policy boundary. A steer.delivered event and a run.steer audit record follow.
  • Pauses. Queued messages are checkpointed in RunState.pending_steering, so they survive an approval, clarification or reconciliation pause and are delivered after the resume.
  • Run ends first. Messages still waiting are RunResult.undelivered_steering, announced by steer.undelivered, so the host can hand them back or start the next turn with them.
  • Limits. At most 16 waiting messages of 8,000 characters each. Empty or longer text is 422; a full queue, an ended run or a run another process is driving is 409.

Events carry count and messages ({id, chars}); the text only with content telemetry on. Conversation turns do not expose steering yet: steer the turn's run by its id (pending.run_id). See Operations · steering.

Sharing a database: postgres_schema#

From 0.1.0a18 storage.postgres_schema keeps the Runtime's tables in their own schema, so they can share a database with an application's own. Every pooled connection starts with search_path set to that schema alone, so migrations and every PostgreSQL store use it; with initialize_schema it is created when missing. The Runtime does not move existing tables; if the schema is empty while public still holds them, start-up logs postgres_schema_is_empty_but_public_has_runtime_tables. Behaviour change in 0.1.0a14. With Traccia on, Traccia receives only the traces the Runtime started. Authentication#

api.auth_mode decides how the service knows who is calling. From 0.1.0a17 it can verify tokens from an OpenID Connect identity provider, revoke tokens before they expire, accept a client-certificate identity from a trusted proxy, and audit every failed sign-in.

New in 0.1.0a17. Install it with python -m pip install "algen-agent-runtime[auth]==0.1.0a17"; jwt and oidc need the auth extra (PyJWT[crypto]). Studio's Runtime floor is still 0.1.0a13, so this applies only where 0.1.0a17 or later is installed.

OIDC issuers and JWKS#

agent.yaml · api.auth_mode: oidc
api:
  host: 0.0.0.0
  auth_mode: oidc
  oidc:
    jwks_cache_ttl_seconds: 300            # how long fetched keys are used (30 to 86400)
    jwks_min_refresh_interval_seconds: 30  # at most one JWKS fetch per issuer per interval
    http_timeout_seconds: 5
    allow_private_networks: false          # true only for an in-cluster identity provider
    issuers:
      - issuer: https://login.example.com/realms/acme   # exact 'iss'
        # jwks_url: https://login.example.com/realms/acme/protocol/openid-connect/certs
        audiences: [algen-agent-runtime]
        algorithms: [RS256]                # RS*, PS*, ES*, EdDSA only
        leeway_seconds: 30                 # clock skew for exp/nbf/iat, at most 300
        max_token_lifetime_seconds: 900    # optional: refuse long-lived tokens
        required_claims: [azp]             # beyond exp, iss, aud and the subject
        claims:
          subject_claim: sub
          tenant_claim: tenant_id          # or fixed_tenant: acme
          allowed_tenants: []              # optional allowlist
          scope_claims: [scope, scp]
          role_claims: [realm_access.roles, groups]
          role_scopes:
            runtime-operators: [runs:read, runs:write, conversations:read]
            runtime-admins: [auth:revoke, tools:reconcile]
  • Discovery. Without jwks_url the Runtime reads {issuer}/.well-known/openid-configuration, requires its issuer to equal the configured one, and fetches its jwks_uri.
  • Egress. Discovery and JWKS fetches use the SSRF-safe client and reach only the issuer host, the jwks_url host and the issuer's additional_allowed_hosts. Private, loopback, link-local and metadata addresses are refused unless allow_private_networks: true; redirects are not followed; responses are capped at max_jwks_bytes (256 KiB); https is required unless allow_insecure_http: true (local test providers only).
  • Caching and rotation. Keys are cached for jwks_cache_ttl_seconds. A token with an unknown kid triggers a refresh, at most one per jwks_min_refresh_interval_seconds per issuer, so random key ids cannot turn requests into identity-provider traffic. If a refresh fails the last good keys stay in use; if keys were never fetched the API answers 503. Publish a new key before signing with it, and keep the old one published until its tokens have expired.
  • Algorithms. Only the issuer's algorithms are accepted; none and HS* are refused by configuration validation. The token's algorithm must also match the key type (RSA: RS*/PS*, EC: ES*, OKP: EdDSA) and the key's alg when the JWKS states one. Symmetric (oct) keys are ignored, and tokens must carry a kid.
  • Claims. exp, iss, aud and the subject are required; nbf and iat are checked when present, all with leeway_seconds of skew. max_token_lifetime_seconds (60 to 86400) requires iat and refuses tokens that live longer.

Claims to tenant and scopes#

The subject claim becomes the user id. The tenant comes from fixed_tenant (one-tenant issuers; it takes precedence) or tenant_claim (default tenant_id), and allowed_tenants can limit it. A missing, empty or non-string tenant is refused: the tenant fails closed and is never defaulted. Scopes are the union of the scope_claims values (default scope and scp; a space-separated string or a list) and the scopes role_scopes grants for each value in role_claims (default roles and groups). A * in a token's own scope claim is dropped; grant the wildcard through role_scopes if you really need it. Claim names are looked up literally first, for namespaced claims such as https://example.com/tenant, then as dotted paths such as realm_access.roles.

Token revocation#

Short-lived access tokens (5 to 15 minutes, enforced with max_token_lifetime_seconds) are the main revocation control. For a token that must stop working sooner, turn on the check, for jwt and oidc:

agent.yaml · api.token_revocation
api:
  token_revocation:
    enabled: true
    store: postgres     # 'memory' (default) is per process and lost on restart; postgres needs storage.postgres_dsn
    require_jti: false  # true refuses tokens without a jti

Each verified token is then checked, in one store lookup, against a tenant-scoped jti denylist and a per-subject “revoked before” cutoff (a token whose iat is at or before the cutoff, or that has no iat, is refused). A store outage fails closed with 503. Revoke with the auth:revoke scope, within the caller's own tenant:

RouteBodyEffect
POST /v1/auth/revocations/tokens{"jti", "expires_at", "reason"?}Denies the token until its exp; the entry is purged afterwards. expires_at at most a year ahead.
POST /v1/auth/revocations/subjects{"subject", "revoked_before"?, "reason"?}Refuses every token for the subject issued at or before the cutoff (default now, at most five minutes in the future). A cutoff only moves forward.

Both return 404 while revocation is off. From Python use container.token_revocations (revoke_token, revoke_subject, state, purge_expired). The PostgreSQL store uses migration 013_token_revocation.sql, run on startup. The check costs one indexed lookup per request and makes the store a dependency of authentication.

Service identity from a trusted proxy#

When a TLS-terminating proxy verifies client certificates, it can pass the client's identity to the Runtime in a header. This is off by default and needs auth_mode: jwt or oidc.

agent.yaml · api.trusted_proxy_identity
api:
  trusted_proxy_identity:
    enabled: true
    header: x-client-cert-identity
    trusted_proxies: [10.0.0.0/24]       # CIDRs of the proxies, never 0.0.0.0/0
    identities:
      spiffe://acme/ns/jobs/sa/scheduler:
        tenant_id: acme
        user_id: svc-scheduler           # default: the identity string
        scopes: [runs:write, runs:read]
  • CIDR rule. The header is honoured only when the request's direct TCP peer is inside trusted_proxies. A network that covers every address (prefix length 0, such as 0.0.0.0/0) is refused, and an enabled hook needs at least one proxy and one identity.
  • Exact identities. Only a value listed in identities is accepted; any other value is refused. The same header from any other address is refused and audited as untrusted_proxy, even when the request also carries a valid bearer token. Requests without the header fall through to bearer authentication.
  • Header. It may not be a header that already carries identity (authorization, cookie, x-tenant-id, x-forwarded-for and the like). The proxy must overwrite it on every request and never pass a client's value through.
  • Peer address. algen-agent-runtime serve disables uvicorn's X-Forwarded-For rewriting while the hook is enabled; under another server, disable proxy-header rewriting there too. mTLS terminated by the Runtime itself is not mapped to principals.

Start and drain#

created→ starting→ ready→ draining→ stopped

Container.lifecycle.phase is reported as lifecycle. Startup (Container.astart, run by the FastAPI lifespan) starts resources, discovers MCP tools, recovers incomplete agent runs and conversations, recovers the workflow service's interrupted runs, and starts the maintenance loop when maintenance.enabled. Shutdown (Container.aclose) moves to draining, so readiness fails at once, then stops the maintenance loop; drains the workflow service for shutdown_grace_seconds; drains conversations and agent runs with the same grace period; closes retrievers and resources; and moves to stopped. Interrupted agent runs keep a recoverable status and interrupted workflow runs keep their last checkpoint. See Service workflow lifecycle.

Set the orchestrator's termination grace period above shutdown_grace_seconds × 3 plus a margin, so the drain completes before the process is killed. See Operations · readiness and lifecycle.

Production checklist#

Pre-alpha does not mean prototype, but deployment claims must stay narrow. Before serving external traffic, validate the complete operator boundary.

  1. Threat-model the deploymentDefine trust boundaries for API clients, model providers, tool processes, MCP servers, stores, artifacts, and telemetry exporters.
  2. Externalize durable stateConfigure production stores, migrations, backups, retention, reconciliation, and tenant-isolation verification.
  3. Constrain every egress pathUse secret references, outbound allowlists, TLS verification, safe transports, request limits, and provider-specific timeouts.
  4. Authenticate the serviceReplace development headers with JWT, configure CORS deliberately, and keep the Agent Manifest UI internal.
  5. Prove recoveryExercise worker interruption, approval resume, duplicate delivery, tool indeterminacy, workflow fingerprint mismatch, and store degradation.

Per-run caller credentials. Credentials passed to start, run or resume live only in the process's memory, keyed by run, while it executes; no store, exporter, log line or traceback can hold them. A pause can outlast a token, so supply fresh credentials on every resume, and have tools refuse to act when the mapping is empty. Tools must not echo them in results or errors, which reach the model, events and stores. See Credentials of the caller and the threat model.

Readiness and drain. Point the readiness probe at /health/ready and decide what must be up: list it under runtime.readiness.required, or set model_providers: all. Alert on status: degraded with HTTP 200 as well as on 503. Give the orchestrator a termination grace period above shutdown_grace_seconds × 3, and run one Runtime process per deployment while conversation turns can wait. See Readiness & lifecycle.

Identity. Use auth_mode: oidc (or jwt) outside loopback development; require short-lived tokens with max_token_lifetime_seconds, map tenants explicitly, and turn on token_revocation with the postgres store when tokens must be revocable before they expire. Enable trusted_proxy_identity only behind a proxy that verifies client certificates and overwrites the header, listing only its own CIDRs. See Authentication.

Unknown tool outcomes. Grant tools:reconcile to operators only, watch GET /v1/tool-executions or the tool.reconciliation_required event, give side-effecting tools a reconcile hook where the external system can answer, and use on_indeterminate: pause for agents that should wait rather than fail. See Side-effect operations.

Store outages and upgrades. Run one Runtime process per database or postgres_schema, point postgres_dsn at an endpoint that follows the primary, and have clients retry 503 with Retry-After. Back up the whole database in one snapshot before every upgrade, and run the 0.1.0a18 upgrade (migration 016) in a quiet period. See Store outages.

Policies. Ship company-wide rules as signed bundles with require_signed: true and min_version, keep the signing key in your release pipeline, and alert on any policy.error record with outcome fail_open. See Policy bundles & fail modes.

Egress, processes and plugins. Send outbound traffic through network.egress_proxy with its own egress policy, pin or mTLS-authenticate partner APIs under network.remotes, set security.sandbox.required: true with a wrapper wherever stdio MCP servers or core.subprocess run, and set plugins.require_signed: true with read-only plugin packages. See Egress, sandbox & signing.

Bounds. Lower max_model_calls, max_response_chars and max_events for agents that face untrusted input, set storage.quotas per tenant, turn on the retention windows, and grant approvals:read, approvals:decide, runs:admin and usage:read on purpose. See Limits, quotas & retention.

Troubleshooting#

Configuration fails to load with an unknown or extra field.

Settings are strict: unknown keys fail fast instead of being ignored. Check spelling against the schema, and make sure environment variables use the ALGEN_AGENT_RUNTIME__ prefix with double-underscore nesting.

An agent's model references an unknown provider.

default_model.provider, fallback models, and embedding providers must name a configured provider instance key (for example local), not the adapter type.

max_concurrent_runs_per_tenant is rejected.

The alias was removed in 0.1.0a4. Rename it to max_concurrent_run_requests_per_tenant, which bounds in-flight POST /v1/runs concurrency.

A manifest is rejected for an unresolved {{…}} placeholder.

Scaffolded templates contain placeholders that must be replaced before loading. Search the project for {{ and fill or remove each one.

An import error says an extra is missing.

Your configuration enables an optional integration. Install the named extra, for example pip install --pre 'algen-agent-runtime[mcp]' or [postgres,redis].

serve refuses to bind to 0.0.0.0.

Development header authentication may bind only to loopback. Switch to api.auth_mode: jwt for shared networks. Setting allow_insecure_development_auth: true is only for an explicitly trusted development network.

HTTP calls return 401, 403, or 429.

401: tenant and user identity are missing. 403: the caller lacks a scope such as runs:write, or acts on another user's run without approvals:decide (approval) or runs:admin (cancel); steering and clarifications are the run's user's only. 429: a tenant rate limit was hit — honor Retry-After.

/agent-ui returns 404.

The route is disabled by default. Set api.agent_ui_enabled: true or start with serve --ui.

An MCP server header is rejected as a literal secret.

Sensitive headers and tokens must be env:// references via auth_token_ref or secret_headers.

A tool call is answered with "ok": false and “Invalid arguments”.

From 0.1.0a14 arguments are checked against the tool's input_schema before the call runs or any approval is created. The error names where the arguments do not fit; fix the tool's schema or the agent's instructions. A fail_run agent fails on it instead.

An MCP tool returns MCPNotConnected.

The server uses OAuth and the caller (or, for token_scope: tenant, the tenant) has no usable connection. Start one with POST /v1/mcp/servers/{server}/oauth/start, the start_path in the mcp.auth_required event. With the in-memory store, a restart forgets every connection.

A run failed with reason: budget_refused.

The deployment's usage meter raised MeterRefusedError; its message is on RunState.error and the budget.refused event. It is not a provider failure and is not retried.

A run failed with reason: budget_refused.

The deployment's usage meter raised MeterRefusedError; its message is on RunState.error and the budget.refused event. The event and its audit record name the provider and model whose reservation was refused, so you can tell which account or model ran out. It is not a provider failure and is not retried.

A DeprecationWarning says the usage meter's reserve has no call parameter.

The meter uses the 0.1.0a14 form. It still works and is charged as before, but the form is removed in 0.2: add call: MeterCall to reserve. See Usage metering.

A ConfigurationError says the usage meter's reserve() has no call parameter.

The meter uses the 0.1.0a14 form, which was removed in 0.2, so the router refuses it when it is built. Add call: MeterCall to reserve. See Usage metering.

A tool says “authentication required” after an approval.

Caller credentials are kept in memory only and dropped when the run pauses. Pass them again with runtime.resume(..., credentials=...); a run recovered after a restart, or started from a workflow or the HTTP API, has none. See Credentials of the caller.

FastAPI request spans no longer appear in Traccia.

From 0.1.0a14 Traccia receives only traces the Runtime started. Set telemetry.traccia.export_foreign_traces: true to send everything as before.

A new conversation message gets 409.

From 0.1.0a16 a turn whose run waits for an approval or an answer stays awaiting_approval or awaiting_input, and only one turn per conversation can wait. The 409 names the waiting turn id: answer it with POST /v1/conversations/{id}/turns/{turn_id}/approval or /input (or ConversationService.respond), or cancel it with DELETE /v1/conversations/{id}/active-response, which cancels its run too. See Conversation turns.

/health/ready says degraded, or returns 503.

degraded with HTTP 200 means an optional dependency is down (a cache, a retriever, an optional MCP server, or workflow.recovery): the service still takes traffic, and degraded_dependencies says why. 503 with degraded means a required dependency is down or no model provider is healthy: failing names it. 503 with draining means the service is shutting down. Adjust what is required with runtime.readiness. See Readiness & lifecycle.

A workflow run was not recovered after a restart.

The service recovers only runs it owns (owner: workflow_service). Runs started through the HTTP API before 0.1.0a16, and runs an application started with its own executor, have no owner: decide or answer them through the API, or recover them once with executor.recover. An owned run is also left untouched, and logged, when its manifest changed or is no longer configured, or its hooks are not trusted; and a waiting run is not resumed by recovery. See Service workflow lifecycle.

Calls get 401 with WWW-Authenticate: Bearer error="invalid_token".

The bearer token was refused. From 0.1.0a17 the answer is the same for every reason; the reason is in the auth.authenticate audit record (tenant _authentication unless the token was verified), the authentication failed log and the algen_agent_runtime.auth.attempts metric. Common ones: expired or not_yet_valid (clock skew beyond leeway_seconds), invalid_audience, unknown_issuer (the iss does not exactly match a configured issuer), unknown_key (a kid not yet in the JWKS; refreshes are rate-limited), missing_tenant (no tenant claim and no fixed_tenant), token_lifetime_exceeded, and revoked. See Authentication.

Calls get 503 when the identity provider or revocation store is down.

Authentication fails closed. keys_unavailable: the Runtime has never fetched the issuer's JWKS (once fetched, the last good keys stay in use while refreshes fail); check discovery, the jwks_url host and egress (additional_allowed_hosts, allow_private_networks for an in-cluster provider, https). revocation_unavailable: token_revocation is on and its store cannot be read; restore the database, or turn the check off knowingly. See OIDC issuers and JWKS and Token revocation.

A run stays in awaiting_reconciliation.

The agent has tool_policy.on_indeterminate: pause and a side-effecting call's outcome is unknown. The run waits, without expiring, until someone with tools:reconcile settles the call: find it with GET /v1/tool-executions?run_id=…, then reconcile, resolve or compensate it. If the call is already settled but the run still waits (the Runtime stopped in between), POST /v1/tool-executions/{key}/resume. Cancel the run to give up. See the runbook.

Resolving a tool call returns 409.

The call is not in a state that decision can change. Read it again with GET /v1/tool-executions/{key}: someone else may have decided it first (each decision is a compare-and-set), it may no longer match your expected_status, its outcome may already be known, or it is started and changed less than 10 minutes ago, so it may still be running. reconcile on a tool without a hook, and compensate on one without a compensation or on a call that is not completed, indeterminate or compensation_failed, are 409 too. See Rules.

A schema-constrained step on Claude 5.x fails with HTTP 400 "does not support assistant message prefill".

Before 0.1.0a21 the repair after a failed output check ended the conversation with the model's own answer, which Claude 5.x rejects. Upgrade to 0.1.0a21: the repair is a user message, and schema limits the provider drops are described in the schema it sends.

A long agentic run fails with JSONDecodeError from a provider adapter.

The model wrote a tool call whose arguments are not valid JSON. From 0.1.0a21 that is a retryable InvalidToolCallError and the run asks the model again; look for model.tool_call_invalid audit events to see how often a model does it.

A workflow with a tool: step will not start, or a direct executor call is refused for approval.

From 0.1.0a19 a tool with requires_approval runs only under an approval. Put an approval node upstream of the tool: step, or pass approval= when calling ToolExecutor.execute yourself. See Human approvals.

A run with attachments is refused before any model call.

The agent did not opt in (attachments.enabled), a file is not available yet (uploads stay pending_scan until scanned; set security.upload_scanner: basic), its real type is not allowed, a limit is exceeded, or no configured model reports images (or files for PDF). The error names which. See File attachments.

The service started but a toolkit's tools fail with a configuration error.

From 0.1.0a19 a toolkit that cannot start degrades readiness instead of stopping the service. From 0.1.0a20 its calls raise ToolkitConfigurationError with what to set or install. Fix the setting, or build the toolkit with required=True to fail at start.

Calls get 503 with Retry-After while the database is down.

From 0.1.0a18 a PostgreSQL or Redis store that cannot be reached, times out or is shutting down raises StoreUnavailableError, answered with 503 instead of 500. Retry after the header's delay. Runs in flight keep their checkpoint and continue when the store is back. If calls time out on a slow but healthy database, raise storage.postgres_command_timeout_seconds (60 by default) or redis_socket_timeout_seconds (10). See Store outages.

A write gets 413 with code: QUOTA_EXCEEDED.

The tenant reached a storage.quotas limit; resource and dimension say which. Retrying cannot succeed: delete data or raise the quota. GET /v1/storage/usage shows usage and limits. A full session-memory quota does not fail a run; it skips the turn's memory. See Storage quotas.

A run or tool call is refused with reason_code: policy.error.

A policy raised or ran past policies.evaluation_timeout_seconds, and the boundary is closed (the default). The policy.error audit record and the policy_error log name the boundary, policy and error type. Fix the policy; set policies.boundary_on_error to open for that boundary only if letting values through without it is acceptable. See Boundaries and fail modes.

A tool call is refused because its arguments carry a token or card number.

From 0.1.0a18 the secrets policy redacts bearer tokens and the pii policy card numbers, and a redacted tool argument refuses the call at before_tool. Pass credentials to tools as env:// references or caller credentials (auth.type: caller for HTTP tools), never as argument values. UUIDs, hashes and other identifiers are no longer mistaken for phone or Aadhaar numbers.

A run failed with reason: limit_exceeded.

The run reached a per-run limit; limit on the run.failed event names it (model_calls, response_chars, events, or a step, token or cost limit). Raise it on the agent's budget only if the run is legitimate; a run that keeps reaching one is usually looping. See Run limits.

Start-up refuses a policy bundle or plugin.

A bundle's signature does not verify against trusted_keys, it is unsigned with require_signed: true, expired, issued in the future, or below min_version; check it with algen-agent-runtime policy verify. A plugin is unsigned or not from a trusted_publishers entry under plugins.require_signed, or a file changed after signing; check it with algen-agent-runtime plugin verify. See Egress, sandbox & signing.

Start-up fails because postgres_schema is not in effect.

The connection's current_schema() is not the configured schema: a pooler in transaction mode dropped the search_path startup parameter, or the role lacks USAGE on the schema. Use session pooling (or add search_path to PgBouncer's track_extra_parameters), grant USAGE and CREATE, or create the schema (or set initialize_schema: true). See Sharing a database.

Resuming a workflow fails with a conflict.

Either the workflow is not paused in the state you expected, or you are resuming with a different manifest name or version than the one that started it. Resume with the exact original manifest.

Glossary#

Agent definition
A versioned agent: default model, instructions, tools, policies, and budget.
Approval node
A workflow node that pauses for an attributed human decision.
Audit event
An immutable evidence record of actor, action, outcome, and resource.
Capability narrowing
Effective capabilities are the intersection of adapter-reported and configured capabilities; widening fails safe.
Checkpoint
Persisted run or workflow state that makes execution recoverable.
Composition root
build_container: the one place where settings become wired runtime components.
env:// reference
A pointer to a secret in the environment, such as env://OPENAI_API_KEY, used instead of a literal.
Hook provider
Trusted Python that supplies named builders, handlers, and schemas to a workflow.
Idempotency
How safely a tool call can be repeated: idempotent, keyed, or non-idempotent.
Provider instance
A named deployment of a model adapter type, with its own health, limits, and cost accounting.
Run event
One typed, sequenced entry in a run's lifecycle stream.
Side effect
A tool's classification — none, read, write, external, or destructive.
Tenant
The isolation boundary carried on every request, store record, and event.
Workflow manifest
A versioned, fingerprinted DAG of nodes declared in YAML.
